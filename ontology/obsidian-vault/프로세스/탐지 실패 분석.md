# 탐지 실패 분석

병목 로직을 고칠 때 과거 결과를 보고 규칙을 맞추지 않도록, 정보 기준일을 고정한 재생(replay)을 한다.

## 미탐지 사례 재생

1. 병목이라고 판단할 역사적 기준일을 고정한다.
2. 그 날짜 이후에 공개된 정보는 제거한다.
3. 당시 유니버스·가격·재무·컨센서스로 다시 실행한다.
4. `universe → derive → aggregate → score → gate → qualitative → handoff` 중 최초 실패 단계를 찾는다.
5. 당시에도 관측 가능했는지와 후행적으로만 알 수 있는 정보를 분리한다.
6. 수정안 하나를 제안하고 미탐지·반대 사례를 함께 재실행한다.

## HBM·DRAM 점검 질문

- 메모리 전체인가, 특정 세대·대역폭·패키징 공정인가?
- 최종수요 신호가 서버·가속기 고객의 주문·CAPEX로 관측됐는가?
- 공급 제약이 웨이퍼·패키징·검사·장비 중 어느 단계였는가?
- 산업 그룹 평균에 하위 병목의 성장·마진이 희석됐는가?
- 당시 가격·마진 자료가 존재했는데 점수나 게이트에서 탈락했는가?
- 뒤늦은 수요 전망을 당시 정보로 착각하고 있지 않은가?

## 수정 승인 기준

- 최초 실패 단계와 당시 사용 가능했던 정보
- 새 규칙이 포착하는 경제적 메커니즘
- 반대 사례를 더 통과시키지 않는지
- 수정 전·후 재현 결과
- 새 규칙의 데이터 요구사항과 결측 처리

과거 사례가 나중에 크게 올랐다는 사실만으로 가중치를 바꾸지 않는다. 데이터가 당시 존재했는지부터 확인한다.
